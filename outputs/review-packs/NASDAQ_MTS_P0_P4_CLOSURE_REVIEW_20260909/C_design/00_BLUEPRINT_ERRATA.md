# 설계도 정오표 — §2 "현 위치"는 이 팩보다 낡았다

**작성 2026-09-09 · 기계 대조로 확인**

`mts_program_blueprint_v1_260909.md` 는 이 팩의 통치 문서지만, 그 안의 **현 위치 수치(§2)는
같은 날 오전에 찍힌 스냅샷**이다. 그날 오후에 P2(홀드아웃 소모)와 P4(rung-4)가 실행되면서
아래 값들이 바뀌었다. 검토관이 §2를 최신으로 읽으면 잘못된 판정을 하게 되므로 먼저 밝힌다.

| 항목 | 설계도 §2 기재 | 현재 사실 | 확인 파일 |
|---|---|---|---|
| 홀드아웃 슬롯 | 0/3 소모 (미소모) | **1/3 소모 — partial(3/9 통과)** | `E_artifacts/ledgers/holdout_scorings.jsonl` (1행), `01_STATE/FACTS.json` |
| 개발 평가 예산 | 3/8 | **4/8** | 계약 `development_protocol.evaluations_spent`, `E_artifacts/ledgers/vol_experiments.jsonl` (4행) |
| 현 단계 | P2 (예시 출력 §9.2) | **P5** | `01_STATE/roadmap_status.txt` |
| P4 상태 | 미착수 | **완료(부정 종료) — 27검정 채택 0** | `E_artifacts/vol/ladder_rung4_macro.json` |
| 라이브 전진 원점 | 1 | **2** (고유 as_of: 2026-09-04, 2026-09-08) | `E_artifacts/ledgers/vol_live.jsonl` (3행 / 고유 2) |

설계도 자신이 §0 에서 이 위험을 경고한다 — *"§2를 최신이라고 가정하지 마라. 진실은 §9.3의
파일·필드다."* 이 정오표는 그 경고를 구체적 수치로 옮긴 것이다.

## 검토관이 §2 대신 볼 것

1. `01_STATE/FACTS.json` — **기계 파생**. 산문을 거치지 않고 계약·원장·산출 JSON 에서 직접 뽑았다.
   다른 문서의 수치가 이것과 다르면 이것이 옳다.
2. `01_STATE/roadmap_status.txt` — 도구 출력. 첫 줄에 읽은 체크아웃과 커밋이 찍혀 있다.
3. `01_STATE/STATE_OF_THE_PROGRAM.md` — 위 둘을 사람이 읽을 형태로 푼 것. 각 판정에 근거 파일·필드가 붙어 있다.

설계도에서 **여전히 유효한 것**은 구조다: 완성 정의 C0~C4(§1), 단계 정의와 종료 조건(§3, §9.3),
판정 기계 표준(§5), 데이터·라이선스 등급(§6), 표시 사다리(§7), 승인 템플릿(§8),
부정 결과 프로토콜(§10). 낡은 것은 **상태 값뿐**이다.

## 이것이 드러내는 설계상 논점

설계도 §9.4 는 "상태를 손으로 적는 파일을 만들지 않는다 — 낡은 상태 파일은 잘못된 다음 행동을
부른다"고 못박는다. 그런데 설계도 §2 자체가 손으로 적은 상태다. 예고됐던 기계 판독본
`data/contracts/mts_program_roadmap.yaml` 은 **만들지 않았다** — 그것 역시 손으로 적는 상태
파일이 될 것이기 때문이다. 대신 `tools/roadmap_status.py` 가 원장·계약에서 상태를 파생한다.

이 판단이 옳은지는 검토 질문에 포함돼 있다(`00_REVIEW_REQUEST.md`). 대안은 **단계 정의와 종료
조건만 담고 상태 값은 담지 않는** 스키마 계약을 두는 것이다.
